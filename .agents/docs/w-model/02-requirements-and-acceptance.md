# 要件定義と受入テスト設計

## 目的と適用範囲

Feature要求を、利用者・業務の期待と検証方法が対応した仕様へ具体化します。Feature仕様の正本は `docs/10-features/<feature>.md`、横断する業務仕様は `docs/20-common/`、受入テストの方針・観点は `docs/50-test/` に置きます。配置と識別子は[共通原則](01-common-principles.md)に従います。

この規約は要件の作成・レビュー・受入検証の設計を定めます。実装手段や詳細設計をFeature要求へ混在させず、必要なArchitecture・設計成果物は後続工程で扱います。

## 要求から仕様への整理

要求をそのまま仕様として確定せず、次を区別して記録します。

1. **要求の出典**：依頼・利用者・業務上の背景と、要求を確認した相手。
2. **REQ**：誰が何を達成するか、必要な条件・制約・例外を含む検証可能な要求。
3. **AC**：REQを満たしたと判断できる観測可能な結果。正常系だけでなく、該当する境界値・拒否・失敗時の結果も定義する。
4. **業務ルール**：機能をまたいで再利用するなら `docs/20-common/` の正本を参照し、Feature固有ならFeature仕様内に記録する。
5. **参照**：関連する用語・共通仕様・Architecture上の既知の制約へ相対リンクを付ける。情報源がない前提を事実として補わない。

識別子は[共通原則](01-common-principles.md#識別子と参照)の `REQ-<FEATURE>-NNN` と `AC-<FEATURE>-NNN` を使います。Feature略号はRepository内で一意にし、各REQを1つ以上のACで検証できるようにします。ACは関連REQ IDを明記します。

REQには、必要に応じて主体、目的、事前条件、入力、期待結果、制約、失敗時の扱いを含めます。ACにはGiven/When/Then相当の前提・操作・期待結果を具体化し、曖昧な語（「速い」「適切」「簡単」など）を測定可能な条件へ変換するか、未確定事項として質問にします。相互に矛盾する要求はどちらかを黙って選ばず、影響と選択肢を記録します。

各Feature仕様には次を記録します。

- 目的・スコープ（含むこと／含まないこと）
- REQとAC、および両者のIDによる対応
- Feature固有の業務ルール、共通仕様へのリンク
- 受入テスト観点とシナリオへの参照
- 未確定事項、質問、決定者、回答期限または判断待ちの状態
- 仕様レビューと人間による確定の状態・記録

## 受入テスト設計

受入テストはFeature仕様のREQ・ACを利用者視点で検証します。まず観点を列挙し、要求に関係するものを選びます。すべてを機械的に適用するのではなく、非該当の場合は理由を記録します。

- 正常な利用経路と主要な代替経路
- 必須・任意・欠落・不正な入力
- 境界値（最小、最大、上限の直前・直後など）
- 業務ルール、権限・状態・重複などの制約
- エラー時の利用者向け結果と副作用がないこと
- 要求に含まれる場合の性能・可用性・アクセシビリティ等の非機能条件

各受入ケースに安定した `TEST-<FEATURE>-ACC-NNN` を付与し、関連するREQ/AC IDと期待結果を示します。テスト方針・意図・観点は `docs/50-test/acceptance/` に置き、実行可能なテストは `tests/acceptance/` に置きます。両者の内容を二重管理しないよう、実行可能仕様を採用した場合はそれを正本として文書から参照します。

### BDD / Gherkin を採用する場合

- 実行可能な受入仕様を `tests/acceptance/<feature>.feature` に置き、REQ/AC IDをタグ等で追跡できる形で付けます。
- Feature仕様にはシナリオを複製せず、`.feature`へのリンクと対応するREQ/AC IDを記録します。
- `.feature`のScenarioは利用者が理解できる言葉で結果を記述し、実装内部の手順やUI上の細かなクリック列に依存させません。
- ステップ定義とテスト実行環境はコード側に置き、`.feature`を実際に実行・検証できる状態を保ちます。

### BDD を採用しない場合

- `docs/50-test/acceptance/<feature>.md` に受入シナリオとテスト観点を記録します。
- 各ケースにTEST ID、関連REQ/AC ID、前提、操作、期待結果、必要なテストデータを記載します。
- 実行可能な自動テストを作る場合は `tests/acceptance/` に置き、文書のケースを参照元とするか、実行可能テストを正本にして文書からリンクします。

## 独立レビュー

作成者とは異なるレビュアーが、確定前のFeature仕様と受入テスト設計を確認します。レビューには要求の出典、Feature仕様、参照した共通仕様、受入仕様、未確定事項を渡します。少なくとも次を調べます。

- 要求の意図がREQに欠落なく反映され、各REQに検証可能なACがあるか。
- REQ/AC間、業務ルール間、既存仕様との曖昧さ・矛盾・重複がないか。
- 主体、条件、境界、例外、失敗時の結果など、受入観点に抜けがないか。
- ACから受入シナリオを実施し、期待結果を判定できるか。
- 共通ルールを複製せず正本へリンクしているか。参照先とIDが有効か。
- 実装詳細を要求へ先取りしていないか、未確定事項を確定事項として扱っていないか。

指摘は対象IDまたは見出し、問題、影響、解決に必要な確認を示し、必須修正と提案を区別します。指摘の解決後、影響したREQ/AC・テスト観点を再確認します。レビュー記録には対象Revision、レビュアー、判定、指摘と状態を残します。

### 要件・受入ゲート

Feature仕様（要求出典、REQ、AC）と受入仕様（BDDなら実行可能な`.feature`、非BDDなら受入仕様書）は必須の対です。Reviewerは同一Revisionの両方を取得し、REQ/ACから受入ケースと期待結果を追跡できることを独立に確認します。どちらかが欠ける、受入判定不能、レビュー未実施、必須指摘未解決の場合は工程未完了とし、Architecture工程へ進みません。両方の正本・ID・Revision、レビュー結果、未解決事項、次工程へ渡す入力と開始許可者・日時を記録します。要件Human Gateが必要な場合、その承認記録も別に揃うまで後続工程を開始しません。

## 未確定事項と Human Gate

未確定事項は `OPEN` として明示し、質問、影響するREQ/AC、判断が必要な理由、選択肢（ある場合）、判断者を記録します。未確定事項を勝手な仮定で埋めず、仮定を用いた検討が必要なら仮定と影響を識別して記載します。

要件・ACの確定は人間の判断を要するHuman Gateです。独立レビューが完了し、ブロッキング指摘が解決し、未確定事項が人間に提示された後に、権限を持つ人が仕様を承認します。承認者・日付・対象Revisionと、未解決事項の決定または明示的な保留範囲を記録します。保留事項が対象Featureの振る舞いを左右する場合、該当する仕様を確定扱いにせず、Architecture・Task分解・実装など後続工程へ進めません。

## Feature仕様の記入例

顧客CSV取込の要求を、識別子・業務ルール・共通仕様への参照および受入シナリオへつなぐ最小例です。未提示の詳細を推測せず、決定が必要な点はOPENのままにします。

```markdown
# 顧客CSV取込

## 目的・スコープ
顧客情報をCSVから一括登録する。ファイル上限と部分登録の可否は未確定。

## Requirements
- REQ-CI-001: 登録担当者はCSVを取り込み、各有効行の顧客を登録できる。
- REQ-CI-002: CSVに不正行がある場合、行と理由を特定でき、登録結果は承認済みの一貫したルールに従う。

## Acceptance Criteria
- AC-CI-001 (REQ-CI-001): 有効なCSVを取り込むと、各データ行に対応する顧客が登録され、結果件数を確認できる。
- AC-CI-002 (REQ-CI-002): 不正行があると行番号と理由を確認できる。部分登録の有無は決定後に期待結果を確定する。

## Business Rules
- 顧客IDの一意性は共通仕様を参照する。正本が存在する場合の参照例: `../20-common/customer-identifiers.md#一意性`（REQ-CI-001 / AC-CI-001に適用）。正本または規則が未確定ならOPENとし、確定後に実在する見出しへリンクする。

## Acceptance tests
- `TEST-CI-ACC-001`（REQ-CI-001 / AC-CI-001）— 前提: 一意な顧客IDを持つ1行の有効CSVがある。操作: 登録担当者がCSVを取り込む。期待結果: 顧客が1件登録され、成功件数1件を確認できる。
- `TEST-CI-ACC-002`（REQ-CI-002 / AC-CI-002）— 前提: 1つ以上の不正行を含むCSVがある。操作: 登録担当者がCSVを取り込む。期待結果: 不正行の番号と理由が示される。部分登録の扱いがOPENの間、このケースは結果表示のみを確認する暫定ケースであり、登録結果の合否判定および後続工程での利用は禁止。決定後に期待する登録状態を追記してケースを確定する。

## Open decisions
- OPEN: 不正行がある場合に有効行も登録するか。影響: REQ-CI-002, AC-CI-002。判断者: 業務責任者。
- OPEN: ファイルサイズ・行数の上限。影響: REQ-CI-001の制約と境界値受入テスト。判断者: 業務責任者。
```
