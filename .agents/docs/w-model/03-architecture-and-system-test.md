# Architectureとシステムテスト設計

## 目的と適用範囲

この規約は、確定済みまたは明示的に保留範囲を限定したREQ・ACを、システム境界、構成要素、責務、外部依存、運用・非機能制約へ落とし込み、対応するシステムテスト観点を同時に設計する手順を定めます。Architectureはシステム全体の重要な構造・制約を扱い、実装の逐語的な説明や詳細設計の代替にはしません。

正本は[共通原則](01-common-principles.md#正本ssotと配置)に従い、Architectureを`docs/30-architecture/`、システムテスト方針・観点を`docs/50-test/`、重要な設計判断を`docs/60-adr/`に配置します。各FeatureのArchitecture・システムテスト成果物は、既存Repositoryに確立した正本がなければ`docs/30-architecture/<feature>.md`、`docs/50-test/system/<feature>.md`とします。横断的なArchitectureまたはシステムテスト方針はそれぞれのディレクトリに別途置き、Feature成果物から参照します。

## 入力と前提

- 要件定義済みのFeature仕様、REQ・AC、関連受入仕様と未確定事項。
- システム境界、既存Architecture、用語、共通仕様、外部システムや運用環境について取得可能な情報源。
- RepositoryのFeature略号・既存IDと規定された成果物配置。
- Architecture判断の決定権者、承認方法。分からない場合は未確定として提示します。

要件・受入条件が未確定、参照Architectureが不明、外部契約に矛盾がある場合は、その影響と質問を記録します。推測で制約・外部依存・品質目標を事実化しません。未決事項が構成やシステムテストの合否に影響するなら、影響範囲をOPENとして後続工程を止めます。

## Architecture設計

要求から実装技術を直ちに選ぶのではなく、根拠と制約を追跡できる形で以下を記録します。

1. **境界とコンテキスト**：システムが提供する責務、利用者・外部システムとの境界、データや信頼境界。情報源と未確認範囲を示します。
2. **構成要素と責務**：主要コンポーネント、責務、REQ/ACとの関係、コンポーネント間および外部との関係。必要に応じてデータフローや実行・配備環境を示します。
3. **制約と品質属性**：機能上の境界、セキュリティ、性能、可用性、容量、運用、復旧、プライバシー等の該当する品質属性と、その根拠・測定条件。適用しない属性も理由を残します。
4. **外部依存と運用**：外部サービス、バージョン・契約・責任範囲、障害時の振る舞い、監視・バックアップ・復旧等。未確認のSLAや運用能力はOPENとします。
5. **判断と代替案**：重要な選択、その根拠、制約、検討した代替案と影響をADRへ分離します。承認前は提案・保留として示します。
6. **検証への対応**：Architecture上の各制約・品質目標がどのシステムテストで確認されるかをIDで相互参照します。

Architectureの詳細度は、主要な境界・責務・制約・失敗時の振る舞いをレビューし検証できる最小限とします。コンポーネント内部のアルゴリズム、コード構造、詳細なAPIフィールドなどは、必要なFeatureの詳細設計へ委ねます。

## システムテスト設計

システムテストは結合済みシステムと外部境界を対象にし、Architecture、REQ/AC、非機能制約に対する観測可能な期待結果を定めます。テスト文書には方針・観点・前提・データ・環境・計測方法・期待結果を記録し、実行可能なテストは`tests/system/`に配置します。実行可能テストを正本とする場合、同一シナリオを文書へ複製せず、安定したTEST IDで参照します。

各ケースは`TEST-<FEATURE>-SYS-NNN`を付与し、少なくとも関連REQ/ACまたはArchitecture制約、前提、刺激・条件、観測点、期待結果、必要なデータ・環境、判定方法を示します。対象に応じて正常・境界・負荷・障害・復旧・セキュリティ・外部連携・運用を検討し、該当しない観点は理由を記録します。

非機能要件は曖昧な品質語だけで済ませず、適用する指標、負荷・環境条件、測定窓、許容値、観測方法、合否閾値をREQ/ACまたはArchitecture制約で決め、それらをシステムテストへ結び付けます。情報源に閾値がない場合は、候補を提案として識別し、決定者の承認までOPENとします。未決の候補値を合否基準として用いません。

## 独立レビュー

Architecture作成者とは異なる担当者が、要件・参照仕様・Architecture・ADR案・システムテスト設計を対象Revisionとともに確認します。少なくとも次を検討します。

- REQ/ACの意図と範囲が漏れなく構成、責務、制約へ反映されているか。
- システム境界、外部依存、データフロー、信頼境界、運用条件の根拠が明示されているか。
- 品質属性が測定可能な条件と結び付き、要件・期待結果・テスト観点が追跡できるか。
- 重要な判断に根拠・代替案・影響・承認者があり、推測や暗黙の確定がないか。
- テストを記載された環境・データ・観測方法で実施し、期待結果から合否を判定できるか。
- 詳細設計との重複、要件との矛盾、欠落・壊れたIDや参照がないか。

指摘は対象ID・見出し、問題、影響、解決に必要な確認を示し、必須修正と提案を区別します。必須指摘を解消した後、影響したArchitecture・判断・テストを再確認し、結果を記録します。

## Architecture判断のHuman GateとADR

システム境界、データ保護、外部サービス選定、可用性・復旧方式、技術・運用制約など、後続工程やリスクへ大きく影響する判断は、Architectureを確定する前に決定権を持つ人の承認を得ます。どの判断を重要とみなすかを機械的な金額・規模だけで決めず、影響、不可逆性、リスク、利害関係者への影響を説明します。

重要な判断は`docs/60-adr/ADR-NNN-<短い題名>.md`へ記録します。ADRは少なくともID、題名、状態、日付、決定者・承認者、背景・制約、決定内容、検討した代替案とトレードオフ、関連REQ/AC・Architecture・システムテストを含みます。状態は`Proposed`、`Accepted`、`Rejected`、`Superseded`を使い、承認待ちの判断は`Proposed`のままにします。承認後は承認者、承認日、対象Revisionを記録し、Architectureとシステムテストへ決定を反映します。置き換えられたADRは履歴として残し、後続ADRへリンクします。

独立レビューのブロッキング指摘が残る、重要判断が未承認、または未確定事項が構成・合否に影響する場合、対象を確定Architectureとして扱わず、影響する後続工程へ進みません。人間が承認した保留範囲がある場合は、承認範囲と進行禁止範囲、影響するIDを明記します。

## 記録例：顧客CSV取込（説明用の提案）

以下は設計成果物の関係を示す例であり、実プロジェクトの要件・選定・承認を表すものではありません。CSV取込のREQ/AC IDは既存の[要件定義の記入例](02-requirements-and-acceptance.md#feature仕様の記入例)を参照します。

| Architecture上の要素・制約 | 責務・根拠 | システムテストと期待結果 |
|---|---|---|
| 取込API境界 → 取込オーケストレーター → 顧客Repository | API境界で要求を受け、オーケストレーターが解析・検証・登録処理を調整し、Repositoryが永続化を担う。責務分割は設計案であり、既存実装・要求との整合を確認する。 | `TEST-CI-SYS-001`：有効なCSVをシステム境界から送信すると、受入ACで定めた顧客と結果件数が確認できる。 |
| 不正入力時のエラー境界 | 不正行の識別可能な結果はREQ-CI-002に従う。部分登録の扱いはOPENのため、登録状態の期待結果は確定しない。 | `TEST-CI-SYS-002`：不正行の番号・理由が示される。部分登録の決定がOPENの間は登録状態の合否判定をせず、後続工程へ使用しない。 |
| 性能目標（提案・OPEN） | 性能要求が必要か、CSVサイズ・同時実行数・測定環境・応答時間閾値を決定者が定める。例示目標を合意済み事実として扱わない。 | `TEST-CI-SYS-003`：承認後に定めるデータ量・負荷・環境で応答時間を測定し、承認済みの閾値内であること。閾値がOPENの間は合否判定を保留する。 |

重要なデータ取扱いや外部サービス選定が必要となる場合は、代替案・影響を調査してADR案を作成します。情報が不足している段階でトランザクション方式、クラウド、暗号化方式等を決定事項として作りません。承認者・対象Revisionが確定するまでADRは`Proposed`とし、関連する設計・テストの確定を保留します。
