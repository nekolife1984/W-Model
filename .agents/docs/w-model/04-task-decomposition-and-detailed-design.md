# Task分解と詳細設計・結合テスト

## 目的と適用範囲

Feature・Storyを、AIが実装・検証・レビューできるTaskへ分解し、各Taskで詳細設計と結合テスト観点を同時に作成する規約です。Featureは利用者価値と仕様の管理単位、Storyは利用者またはシステム上のまとまった振る舞い、Taskは限定した変更と検証を1 PRで完結させる実行単位です。

Task Issueは作業範囲・依存・進捗の正本です。機能仕様はFeature仕様、システム全体の制約はArchitecture、コンポーネント間の契約はTaskの詳細設計、実行可能テストはコードを正本とし、Issueへ仕様を重複記載しません。配置・識別子は[共通原則](01-common-principles.md)に従います。

## 分解方針

### 粒度と完結性

- FeatureからStory、Taskの関係を示し、各TaskがどのREQ・ACを実現するか識別できるようにします。
- Taskの目的と変更対象を限定し、原則として1 PRで完結するサイズにします。目安は簡潔な目的、概ね3〜7件の検証可能な完了条件ですが、件数を満たすために条件を水増ししません。
- 可能な範囲で、要件・設計・実装・検証を含む縦切りにします。工程別の作業しか分けられない場合は、その理由と統合・引き渡し条件を明記します。
- 複数の独立した価値、無関係な変更、広すぎる責務を一つのTaskにまとめません。分割後も、依存先が利用可能になるまで動作不能な中間成果を作る場合は、Task間の契約と統合手順を示します。
- 単体・結合検証を独立して実施可能にし、変更ファイルや影響境界をレビュー可能な範囲に保ちます。

### 依存関係

- 依存Task、先行条件、依存理由を明示します。依存がない場合も「なし」と記載します。
- 依存グラフに循環を作りません。並行着手可能なTaskと、直列化が必要なTaskを区別します。
- 依存先の完了を待たずに定義できる契約は先に確定し、実装の仮定で代替しません。外部仕様や人間の判断が未確定ならOPENとして影響範囲を示し、依存Taskを止めます。
- Feature / Story / Taskの階層や関連付けはRepositoryのIssue機能で表現します。Statusで依存関係を代用しません。

### Task完了条件

各Task Issueには、少なくとも次を含めます。

- 対象・目的と対象外
- 関連する親Feature / Story、REQ・AC・Architecture制約
- 変更対象または影響境界
- 検証可能な完了条件と、それぞれの確認方法
- 依存Task・先行条件・依存理由（ない場合は「なし」）
- 詳細設計・結合テスト成果物の場所または既存正本へのリンク
- 未確定事項と、該当する場合の進行禁止範囲

完了条件は観測できる期待結果で記述します。「実装する」「対応する」だけを条件にせず、正常系・該当する境界・失敗時の振る舞いと検証結果を含めます。別Taskに委ねる条件は、依存先とこのTaskを完了扱いにできる判定を分けます。

## 詳細設計の薄い契約

正本は既存配置がなければ`docs/40-design/<feature>/`です。`DESIGN-<FEATURE>-NNN`を付与し、関連するREQ/AC、Architecture要素、Task Issue、結合テストIDへ相互参照します。設計文書は実装担当と結合テスト担当が独立して期待する振る舞いを解釈できるだけの契約を記録します。

対象に応じ、次の項目から必要なものを選びます。

- **責務と境界**：コンポーネントの責務、所有するデータ、担当しない処理、呼び出し元・依存先。
- **インターフェース**：操作・イベント・メッセージの目的、入力・出力、必須性、型・形式、制約、互換性。詳細なAPIフィールドが他の正本にある場合はリンクします。
- **振る舞い・シーケンス**：契約上重要な処理順、同期・非同期境界、副作用、冪等性や重複要求の扱い。
- **状態と不変条件**：状態、遷移を起こすイベント・ガード、遷移後の結果、禁止状態、並行更新時の制約。
- **データ・トランザクション**：読み書き対象、原子性の範囲、commit/rollback条件、部分成功の可否、整合性境界。
- **例外・失敗**：エラー分類、伝播・変換、再試行・タイムアウト・補償の条件、利用側から観測できる結果。
- **結合検証**：境界ごとの前提、刺激、観測点、期待結果、必要な実環境・テストダブル・データ。

すべての項目を埋めることを目的にせず、適用しない項目と理由を記録します。処理をコードのif/forやメソッド単位で逐語説明せず、コードから自明な構造を複製しません。重要な選択・トレードオフはADRへ分け、未承認の決定を設計契約に確定事項として書きません。

## 結合テスト設計

結合テストの方針・観点・期待結果は`docs/50-test/integration/`、実行可能なテストは`tests/integration/`に置きます。設計要素とケースには`TEST-<FEATURE>-INT-NNN`を付けます。実行可能テストをケースの正本とする場合、同じシナリオをMarkdownへ複製せずIDで参照します。

関連する設計境界に対し、該当する観点を選び、適用しないものは理由を残します。

- 入力・出力の形式、必須性、境界値、不正値
- 呼び出し順、データ変換、状態遷移、重複・順不同イベント
- 永続化、トランザクション、commit/rollback、部分失敗
- エラーの変換・伝播、タイムアウト、再試行、補償
- 外部IF・Adapter・メッセージ境界と契約違反
- 権限・信頼境界、並行実行など設計上重要な制約

各ケースは関連DESIGN・REQ/AC ID、前提、操作・入力、観測点、期待結果、データ・環境、判定方法を記載します。Mock/Stubは対象境界を隔離するために限定して使い、検証対象である連携・永続化・トランザクションを置き換えてしまわないようにします。外部依存を代替した箇所と、実環境で確認する残余リスクを示します。

## 独立レビューと工程ゲート

詳細設計の作成者とは異なる担当者が、Feature仕様、関連Architecture・共通仕様、Task分解、詳細設計、結合テスト観点を同じ対象Revisionでレビューします。少なくとも次を確認します。

- Taskが限定された変更で、完了条件ごとに確認方法があり、1 PRで完結できるか。
- Story / FeatureとREQ・ACの対応が追跡でき、依存が漏れず循環していないか。
- インターフェース、責務、状態遷移、トランザクション、失敗時の契約が一貫し、必要な前提が明示されているか。
- 実装担当とテスト担当が、同じ契約から矛盾しない結果を導けるか。
- 結合テストが契約上の境界・失敗を検証し、期待結果から合否を判定できるか。
- 文書がコードの逐語説明や他の正本との重複になっておらず、ID・リンクが有効か。

指摘には対象IDまたは見出し、問題、影響、必要な修正・確認を示し、必須修正と提案を区別します。必須指摘を解消した後、影響する設計・テストと依存Taskを再確認し、対象Revision・レビュアー・判定・指摘状態を記録します。振る舞い・IF・データ整合性に影響するOPEN事項が残る場合は確定扱いにせず、影響する実装とテストを保留します。
