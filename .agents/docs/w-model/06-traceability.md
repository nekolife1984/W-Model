# トレーサビリティ検証

## 目的と適用範囲

本規約は、Featureの要件から受入条件、設計、コード、テスト設計、実行結果までをたどり、対応の欠落・参照切れ・変更追随漏れを検出する。成果物の内容の正本は各仕様・設計・コード・テストに置き、この規約の対応表は関係と状態を示す索引とする。識別子は[共通原則](01-common-principles.md#識別子と参照)に従う。

## 対応表の配置と形式

各Featureにつき `docs/90-traceability/<feature>.md` を対応表の正本として作成する。既存Repositoryに同等の対応表がある場合は新設せず、既存の正本・配置を使う。表はソース成果物から生成または更新し、本文を対応表へ複製しない。自動生成・検査スクリプトがある場合はそれを使い、ない場合はスキルの手順でID・リンク・状態を照合する。

| REQ ID / 要件リンク | AC ID / 受入検証 | DESIGN ID / 設計リンク | 実装状態・リンク | ACC | SYS | INT | UNIT | 変更・根拠 |
|---|---|---|---|---|---|---|---|---|
| `REQ-CI-001`（`docs/10-features/customer-import.md#req-ci-001`） | `AC-CI-001`（`docs/50-test/acceptance/customer-import.md#test-ci-acc-001`） | —（適用外: 利用者から見える振る舞いのみ） | 実装済み: `src/import/Controller.ts` | `TEST-CI-ACC-001` / 設計済み・未実施 | 適用性=N/A; 実行状態=—; 個別REQにSystem境界/品質制約なし; 代替=`TEST-CI-ACC-001`; 再評価=REQにSystem要件追加 | 適用性=N/A; 実行状態=—; 個別REQに独立契約境界なし; 代替=`TEST-CI-ACC-001`; 再評価=独立IF/永続化契約追加 | 適用性=N/A; 実行状態=—; 独立した局所ロジックなし; 代替=`TEST-CI-ACC-001`; 再評価=局所ロジックを追加 | 初回登録 |

例のリンク先は形式を示す仮のパスであり、実際のFeatureではRepository内の正本に置き換える。各行はREQを起点にし、関連するすべての成果物と必要な検証レベルを記録する。複数の成果物・検証がある場合はIDとリンクを複数併記する。

## 状態と適用性

実装列は「未実装」「実装済み」「適用外」の状態を明記し、実装済みの場合は対応ファイル／シンボルへのリンクを併記する。適用外にはREQ単位で理由を記録する。状態が確認できない場合は未確認とし、空欄を完了扱いしない。

検証列は適用性（適用/N/A）と実行状態（未設計/設計済み・未実施/成功/失敗）を区別して記録する。N/Aは実行状態ではなく適用性の判断であり、実行状態は`—`とする。検証が必要だが未対応の場合は「未設計」とし、完了扱いしない。実行済みの場合はテストIDに加えて、実行記録へのリンク、Revision、実行日またはCI実行IDを根拠として記録する。

適用外（N/A）はテストレベルごと・REQごとに判断し、その対象範囲、該当責務・リスクがない根拠、残余リスク、代替検証IDと期待結果、再評価条件を記録する。N/A判定は対象Revisionで独立確認する。全REQに全レベルのテストを強制しないが、適用する検証がなくてもよいという意味ではない。各REQには少なくとも一つの適切な検証根拠を持たせ、各ACには受入検証を対応付ける。要件の性質により複数レベルが必要な場合は、それぞれ対応付ける。

「適用外（N/A）」と「未実施」を混同しない。テストが必要だがまだ作られていない場合は未設計、作成済みで未実行なら設計済み・未実施とする。実行環境・データ・権限が不足する場合も未実施の理由と影響を記録し、必須テストならQA判定をBLOCKEDとする。環境不足・費用・時間をN/Aの根拠にせず、成功に読み替えない。詳細な状態規則は[テスト運用とQAゲート](07-test-operations-and-qa.md#適用性と実行状態の区別)を参照する。

## 生成・更新・検証手順

1. 対象Featureと比較対象Revisionを定め、Feature仕様の全REQ・ACと廃止済みIDを読み取る。正本のファイル名・配置を確認し、識別子を再採番しない。
2. REQからAC、Architecture・詳細設計、実装ファイル／シンボル、受入・システム・結合・単体テストへ、IDとリポジトリ相対リンクをたどって対応表を生成・更新する。対応表だけを根拠に関係を推定せず、参照元の正本で確認する。
3. 変更前後のREQ/AC・業務ルール、Architecture/ADR、DESIGN/IF/Task契約、実装・テストを比較し、変更起点を分類する。追加・変更・廃止IDから直接・推移的な下流の設計、実装、全テストレベル、Traceability、QAへ依存をたどり、影響あり/なし/不明と必要な再確認を記録する。影響なしの場合も旧PASSを流用せず、新旧Revision・比較した差分・依存ID・理由・確認者を含む新しい判定を記録する。未反映を追随漏れとして扱う。
4. 全REQの対応、参照リンクの存在、全ACの受入検証、設計要素の関連要件、実装・テストの上流要件を逆方向にも照合する。要件に結び付かない実装・テストは、共通基盤・保守目的などの正当な理由が確認できるまで孤立候補として報告する。
5. 各検証の設計状態と実行証跡を確認し、未実装・未実行・適用外を区別する。失敗は失敗のまま記録する。影響する検証は新Revisionで再設計/再実行するまで成功扱いせず、非影響の場合も新たな影響評価を記録する。
6. 対応表に比較対象Revision、更新日、検査方法、検出事項、未解決事項を記録する。自動検査を利用した場合はコマンドと終了結果を記録し、手動照合の場合は照合対象と判断根拠を記録する。

## 報告と完了判定

検出事項は、種別（未対応REQ、参照切れ、孤立成果物、変更追随漏れ、検証未設計、未実行、失敗）、対象ID・リンク、期待される対応、根拠、状態を含めて報告する。未解決事項を解消済みとして扱わない。成果物更新後は対応表と検査を再実行し、対象Revisionを更新する。

対応表の完成は品質承認そのものではない。要求との適合性、独立レビュー、必要なテスト実行、Human Gateは各工程の規約に従う。
