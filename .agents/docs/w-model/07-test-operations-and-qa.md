# テスト運用とQAゲート

## 目的と適用範囲

本規約は、テスト設計・実行とQA判定を一貫して記録し、PR・リリースの判断に必要な証跡と未解決事項を提示する。規約・テスト仕様は「何を、なぜ、どの条件で検証するか」を定め、実行可能テストは「実際の振る舞いが期待結果を満たすか」を判定する。規約やテスト計画を実行結果の代用にせず、実行可能テストを仕様の正本にしない。

各Featureで対象レベル、環境、テストデータ、品質ゲートを定める。適用するテストレベルは対象リスクと変更範囲に応じて選び、全要件への一律な全レベル適用は要求しない。[トレーサビリティ規約](06-traceability.md)の対応表と整合させる。

## テスト成果物と実行可能テスト

- `docs/50-test/`：テスト方針、テストレベル別の目的・対象・前提・データ・環境・期待結果、品質ゲート。変更理由とレビュー根拠を残す。
- `tests/unit/`、`tests/integration/`、`tests/system/`、`tests/acceptance/`：選定したテストレベルに対応する実行可能テスト。リポジトリの既存規約があれば既存配置を優先する。
- CI／テストランナーの出力：実行したテスト、結果、失敗内容、実行環境を特定できる機械生成証跡。ログはリンクまたは安定した実行IDで参照し、仕様本文へ複製しない。
- QAレポート：対象Revision、適用したゲート、レベルごとの状態、証跡、失敗原因、未解決事項、判定をまとめる。QAレポートは承認記録ではない。

テスト設計文書には実装の写しではなく、検証目的・条件・期待結果を記す。テストコードは期待結果を機械的に検査する。仕様変更時は設計文書・テスト・対応表を影響に応じて更新し、同じ内容を複数箇所に正本として持たない。

## テストレベルの責務

| レベル | 主な責務 | 対象と証跡 |
|---|---|---|
| Unit | 単一関数・クラス等の局所ロジック、境界値、例外、状態遷移を高速に検証する。 | 外部I/Oから分離した単位。テストID、実行結果、失敗時の期待値と実測値。 |
| Integration | コンポーネント間のIF、データ変換、永続化・メッセージング等の相互作用を検証する。 | 実際に結合する境界を含む構成。依存サービス・DBの種別と構成、テストデータ、実行結果。 |
| System | 統合されたシステムが機能要件・非機能要件、外部連携、運用制約を満たすか検証する。 | システム相当の構成。環境・設定・負荷条件・外部依存、観測値と期待値。 |
| Acceptance | 利用者・業務上のREQ/ACを満たすか、利用者視点のシナリオで確認する。 | 合意した業務条件・ユーザーシナリオ。AC ID、シナリオ、判定結果、必要な人間の確認。 |

各レベルの責務を重複させる場合は、各テストが検出するリスクと追加価値を説明する。受入判断に人間の観察・業務判断が必要なら、自動テストで代用せず、対象・確認者・判断を記録する。

## Mock / Stub とテストデータ

- Stubは、呼び出しに対して決めた応答を返す依存の代替として使い、入力条件ごとの振る舞いを制御する。
- Mockは、呼び出し回数・引数・順序など相互作用を検証する必要がある境界に限定する。内部実装の細部に結び付いた期待は避ける。
- Unitでは外部システムを原則Fake/Stub等で隔離する。Integration/Systemでは検証対象の境界を実依存で確認し、環境上困難な依存だけを置き換え、置き換えた範囲と未検証リスクを記録する。
- テストデータは再現可能・最小限・テスト間で独立にし、識別可能な実個人データや秘密情報を使わない。生成方法、前提、初期状態、クリーンアップを記録する。
- テスト間で共有・順序依存するデータを避ける。固定データを使う場合は、期待値との関係と更新責任を明確にする。

## 実行順序

1. テスト対象Revision、変更範囲、REQ/AC、設計契約、リスクを確認し、適用するレベルとゲートを決める。
2. テスト観点・環境・データ・期待結果を設計し、Mock/Stubの境界と実依存を明示する。
3. Unitを実行し、局所の失敗を修正する。
4. Integrationを実行し、接続境界・契約を確認する。
5. SystemとAcceptanceを選定した環境・シナリオで実行する。実行コストや環境依存のため順序を変える場合は理由を記録する。
6. 変更後は影響を受けるテストを再実行し、必要な上位レベルの回帰確認を行う。
7. 証跡とトレーサビリティを更新し、QAレポートを作成する。

## 実行状態と証跡

状態は以下のいずれか一つで記録する。

- **成功**：対象Revisionで実行され、期待結果を満たした証跡がある。
- **失敗**：実行され、期待結果を満たさなかった。失敗内容と再現に必要な情報を残す。
- **未実行**：必要な検証だが実行されていない、保留・環境不足・実行不能である。理由、影響、解消責任者または次の行動を記録する。
- **適用外**：対象のリスク・振る舞いに対して該当レベルの検証が不要と判断した。対象単位の理由と代替する検証根拠を記す。

各実行証跡には少なくとも、対象Revision、テストレベルとテストID／コマンド、実行日時またはCI実行ID、環境・重要な設定、状態、結果へのリンクを含める。失敗・未実行・適用外を成功扱いにしない。ログに秘密情報や不要な個人情報を含めない。

### QAレポート形式

```markdown
# QAレポート: <Feature / PR>
- 対象Revision：<commit SHA>
- 判定日：<YYYY-MM-DD>
- 対象範囲・除外範囲：<変更と境界>
- 適用ゲート：<ゲート名と基準の参照>

| レベル | 状態 | テストID / 実行 | 証跡 | 未解決事項 |
|---|---|---|---|---|
| Unit | 成功/失敗/未実行/適用外 | ... | ... | ... |
| Integration | 成功/失敗/未実行/適用外 | ... | ... | ... |
| System | 成功/失敗/未実行/適用外 | ... | ... | ... |
| Acceptance | 成功/失敗/未実行/適用外 | ... | ... | ... |

- 失敗原因と戻り先：<分類、根拠、工程またはなし>
- 追跡性：<トレーサビリティ結果へのリンク>
- QA判定：<PASS / FAIL / BLOCKED> — <根拠>
- Human Gate：<対象判断、承認待ち／承認／却下／保留。QA判定と別欄>
```

## 失敗原因と差し戻し先

失敗は観測事実と原因仮説を分け、ログ・再現結果・変更差分で原因を確認する。原因が複数工程にまたがる場合は各工程と影響を列挙する。原因が特定できない場合は未分類として調査を継続し、都合のよい工程へ断定して戻さない。

| 原因分類 | 典型例 | 差し戻し先・対応 |
|---|---|---|
| 要件・受入条件の曖昧さ／矛盾 | 期待結果を一意に判定できない | 要件・受入設計。該当仕様をOPENに戻し、Human Gateで確定する。 |
| Architecture・システム制約の不足 | 非機能条件、外部連携、運用前提が満たせない | Architecture・システムテスト設計。影響する方式判断はADR/Human Gateへ。 |
| 詳細設計・IF契約の欠落 | 境界条件やデータ契約が不明／不整合 | Task分解・詳細設計・Integration設計。契約と結合テストを更新する。 |
| 実装不具合 | 仕様は明確でコードが期待に反する | 実装・Unit。修正後にUnitと影響する回帰テストを再実行する。 |
| テストの欠陥 | テストデータ、前提、期待値、同期処理等が誤っている | 該当レベルのテスト設計・実装。仕様を独立に再確認してから修正する。 |
| 環境・構成・外部依存 | 環境差、権限、サービス停止、設定誤り | 環境・構成管理。再実行可能な環境を整え、未実行期間を記録する。 |
| トレーサビリティ・証跡不足 | 対象RevisionやREQ/ACと結果が結べない | トレーサビリティ・QA記録。根拠を揃えるまでPASSとしない。 |
| セキュリティ・運用上の問題 | 脆弱性、漏えい、監視・復旧要件違反 | 該当する要件・Architecture・実装工程。機密情報は非公開手順で扱う。 |

差し戻し後は、変更対象に加えて影響範囲を再評価する。テスト修正だけで製品不具合を隠したり、仕様変更だけで既存証跡を成功へ読み替えたりしない。

## QAゲートとHuman Gate

QAは証跡に基づく技術的な判定であり、人間の承認を代行しない。Human Gateは権限を持つ人が未確定の業務・方式・リスク判断を承認するゲートであり、テストが成功しただけでは通過しない。

### PRゲート

PRをQA PASSとするには、少なくとも次を確認する。

- 対象Revisionと変更範囲を特定できる。
- 適用される必須テスト・品質チェックが成功している。
- 適用外の項目は根拠があり、必要な代替検証が示されている。
- 失敗・未実行・未解決のリスクが隠されず、受容者と対応計画が明記されている。
- 必要なREQ/AC、設計、テスト、証跡の対応が追跡できる。
- ブロッキングの独立レビュー指摘が未解決でない。

必須ゲートの失敗、根拠のない適用外、対象Revision不明、未解決のブロッキング事項はFAILまたはBLOCKEDとする。PASSはPRのマージ承認やHuman Gateの承認を意味しない。必須でない検証の未実行を許容する場合は、理由・リスク・判断者を明示する。

### Releaseゲート

リリース前に、PRゲートに加えてリリース対象Revision、対象環境・構成、System/Acceptanceの必要な結果、重大障害・既知問題、運用・ロールバック準備、未解決リスクを確認する。リリース固有の必須基準はFeatureまたはRelease計画で事前に定める。未達項目を隠して合格にせず、リリース保留または権限者による明示的なリスク受容を記録する。

### Human Gate記録

Human Gateが必要な場合、QAレポートと分けて次を記録する。

```markdown
## Human Gate
- 判断対象・選択肢：<内容>
- 根拠・影響するREQ/AC・リスク：<参照>
- QA判定：<PASS / FAIL / BLOCKED とQAレポートへのリンク>
- 判断：<承認／却下／保留>
- 判断者：<権限を持つ人>
- 日時：<YYYY-MM-DD>
- 対象Revision：<commit SHA>
- 条件・保留範囲：<内容またはなし>
```

判断対象の仕様が保留されている場合、その振る舞いに依存する後続工程・リリースを進めない。承認は明示記録が必要であり、沈黙・QA PASS・PRマージから推定しない。
