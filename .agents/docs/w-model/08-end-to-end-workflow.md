# W-Model エンドツーエンド実行フロー

## 目的・適用範囲

本規約は、Feature要求から要件・設計・実装・テスト・QA・PR・Release Gateの判断までを、工程成果物と検証証跡で接続する。Release Gateの承認記録までを対象とし、実際のデプロイ・リリース実施と稼働後の運用は対象外とする。詳細な各工程の作業規約は工程文書・スキルを正本とし、本規約は工程間の順序、開始・終了条件、役割分離、引き継ぎ、停止・再開を定める。

サブエージェントは工程内の限定された作業を行う実行単位であり、専用のカスタムエージェント定義を必要としない。オーケストレーターは工程の選択、入力の準備、独立した担当の起動、結果の確認、ゲート判定、記録を担う。権限のある人間だけがHuman Gate、PR承認、Release承認を行う。

## 役割と実行分離

| 役割 | 責務 | 分離要件 |
|---|---|---|
| Orchestrator | 全体計画、工程選択、依存・状態管理、ゲート評価、引き継ぎ・停止判断。 | 成果物の生成担当の自己承認をしない。 |
| Generator | 指定工程の成果物を、指定された正本・スコープに作成または更新する。 | Reviewer/Testとは別のサブエージェント実行で行う。 |
| Reviewer | Generatorと独立に、要求・契約・差分に対する欠落、矛盾、曖昧さ、規約逸脱を検出する。 | Generatorとは別実行にし、同じ成果物と必要な上流正本だけを渡す。Generatorの自己レビューを独立レビューとしない。 |
| Test Designer / Executor | 適用テストを設計し、または既存の実行可能テストを対象Revisionで実行して証跡を報告する。 | 仕様・実装Generatorとは分離する。実行専任には不要な書き込み権限を与えない。 |
| Human Gate owner | 要件、方式、リスクなど人間判断を承認・却下・保留する。 | AIのQA判定・レビュー結果から承認を推定しない。 |

各呼び出しには利用環境のサブエージェント起動機能で役割・スキルを指定する。カスタムエージェント定義ファイルを追加しない。各スキルの呼び出し規約は [.agents/skills](../../skills/) の工程スキルに従う。

## 工程と開始・終了ゲート

工程は依存順に進める。並列化は、入力正本が確定し、成果間の依存がなく、統合前の照合担当が決まっている場合に限る。工程ごとにスキルが指定する成果物を正本へ保存し、後続工程に必要なID・Revision・制約を渡す。

| 工程 | 開始条件・入力 | 実行役割・スキル | 終了条件と次工程への引き継ぎ |
|---|---|---|---|
| 0. 開始・計画 | Feature要求、対象Repository/branch/base、既存状態を特定。依存Issueと情報保護条件を確認。 | Orchestrator | スコープ、工程順、担当分離、対象成果物・人間判断・検証方法を計画。曖昧な対象や取得不能な変更があれば開始停止。 |
| 1. 要件・受入 | 要求原文、情報源、既存仕様・ID、BDD採否、要件確定者。 | Generator `w-model-requirements` → 別実行Reviewer。受入ケースの作成・レビューも独立実行。 | REQ/ACと要求元の対応、受入設計、レビュー記録、OPEN事項、正本へのリンクが揃う。未解決の必須指摘を修正・再レビュー。振る舞いに影響するOPEN事項はHuman Gateへ停止。 |
| 2. Architecture・System | 確定済みREQ/AC、制約、外部依存、運用・非機能要求。 | Generator `w-model-architecture` → 別実行Reviewer。System Test設計を別担当で実行。 | 責務・境界・制約・ADR判断、REQとの対応、System観点・期待結果が揃い、必須レビュー指摘が解決。必要な方式Human Gateが保留ならTask分解へ進まない。 |
| 3. Task・詳細設計・Integration | 承認済み要件・Architecture、依存関係とスコープ。 | Generator `w-model-task-design` → 各Taskの別実行Reviewer。Integration設計は実装担当と分離。 | Task Issueごとの範囲・依存・完了条件・DESIGN契約・Integration観点が揃い、矛盾と必須指摘がない。依存順を決め、Task単位で次工程へ渡す。 |
| 4. 実装・Unit・Code Review | 着手可能Task、承認済み契約、関連REQ/AC、既存コードとテスト。 | Generator `w-model-implementation` → 独立Code Reviewer。Unitは実装者または別Test担当が作成可能だが、実装レビューを代替しない。 | 契約に沿う実装・Unit、実行結果、差分、残課題が特定され、独立レビューの必須指摘を修正・再レビュー済み。契約変更が必要なら上流工程へ戻す。 |
| 5. 統合検証 | 関連Taskの実装・設計契約が利用可能で、Integration/System/Acceptance環境・データを特定。 | Test Designer / Executorを実装Generatorと別実行で起動。実行可能テストは `w-model-qa` に従って実行。 | 適用テストの状態、証跡、対象Revision、環境、失敗原因・未実行理由を記録。必須テストFAILまたは判定不能は後続QAゲートへPASSとして渡さない。 |
| 6. Traceability・QA | 対象Revision、要求からコード・テスト・実行結果までの正本と証跡。 | `w-model-traceability` と `w-model-qa` を別々に起動。必要なら片方が作成した結果をもう片方が独立照合。 | ID・リンク・影響追随・証跡を照合し、QAレポートにPASS/FAIL/BLOCKED、未解決事項、戻り先を記録。QA PASSでもHuman Gate・PR承認を代替しない。 |
| 7. Human PR Gate | 独立レビュー完了、必須検証とQA結果、最終差分、未解決事項の一覧。 | 人間のPRレビュアー。判断材料の整理はOrchestrator。 | 人間がPR承認・マージ可否を判断。未確定の人間判断・必須レビュー・品質条件が残る場合は保留し、責任者へ提示。AIDE採用RepositoryではAIDEのPR手順も満たす。 |
| 8. Release Gate | マージ済みの対象Revisionに加え、権限者が事前承認したRelease計画・必須基準へのリンク、対象バージョン、環境・構成、System/Acceptance証跡、既知問題、運用監視・ロールバック条件を入力として固定する。必須基準はFeatureまたはRelease計画で事前定義し、曖昧・未定義ならゲートを開始せず計画承認へ差し戻す。 | `w-model-qa` による対象Revision・証跡・基準の評価と、権限を持つRelease承認者による判断。 | QA判定（PASS/FAIL/BLOCKED）とRelease判断（承認／却下／保留）を別欄・別記録に残す。QA PASSはRelease承認を意味せず、リスク受容もQA結果を書き換えない。例外受容時は判断者・日時・対象Revision・対象リスク・期限・緩和策を記録する。必須基準未達または未承認なら実リリースを許可しない。ゲート終了時には判断記録と根拠が取得可能であることを確認する。実際のデプロイ後検証は本規約の範囲外。 |

### 成果物と検証の対による工程ゲート

工程成果物と、それを検証する仕様・ケースは一組です。工程担当は両方を同じスコープ・Revisionで揃え、Orchestratorは独立確認の完了前に次工程へ進めてはいけません。

| 工程 | 開発成果物 | 対応する検証成果物 | 独立確認と終了条件 |
|---|---|---|---|
| 要件・受入 | Feature仕様（REQ/AC） | 受入仕様（BDDなら実行可能な`.feature`、非BDDなら受入仕様書） | Reviewerが要求とREQ/AC、受入仕様の対応・期待結果を確認。片方の欠落、必須指摘、未確定の受入判定があれば停止。 |
| Architecture・System | Architecture・制約・ADR案 | System Test設計（観点、環境、データ、期待結果・判定方法） | Reviewerが設計とSystem Test設計の追跡性・判定可能性を確認。片方の欠落または必須指摘があればTask分解へ進まない。 |
| Task・詳細設計・Integration | Task Issueと詳細設計契約 | Integration仕様（境界、前提、観測点、期待結果、環境・データ） | ReviewerがTask完了条件・契約と結合仕様の対応を確認。片方の欠落または必須指摘があれば実装を開始しない。 |
| 実装・Unit | 実装コード | Unitテストと対象Revisionでの実行結果 | 独立Code Reviewerが実装とテストを確認し、実行結果を照合。テストまたは結果の欠落、失敗・判定不能、必須指摘があれば後続QAへ進まない。 |

各ゲートで、両成果物の正本パス・ID・対象Revision、独立確認者・判定・指摘状態、受け入れた次工程入力、開始許可者・日時を作業記録へ残します。開始許可はHuman Gateを代替せず、許可範囲外の入力・保留事項を下流へ渡してはいけません。欠落・取得不能・不一致は未完了として扱い、推測で補わず該当工程で停止します。

**停止動作の確認例：** Feature仕様が完成していても受入仕様または実行可能な受入`.feature`がない場合、要件ゲートは未通過と記録し、Architecture工程の起動を拒否します。同様に、詳細設計があってもIntegration仕様がないTaskは実装を開始しません。欠落を補った後、同じ対象Revisionで両成果物を独立確認し、ゲート記録を完了してから再開します。

ゲートの確認記録は、少なくとも次のように残します。欠落ケースでは開発成果物の状態が「完成」でも判定は「未通過」で、次工程入力と開始許可は未設定です。

| 試行 | 開発成果物 | 対応する検証成果物 | 独立確認 | 判定・次の動作 |
|---|---|---|---|---|
| 受入仕様欠落 | Feature仕様 `Draft`、REQ/ACあり | なし | 未実施 | `未通過`。Architecture工程を起動せず、受入仕様作成・同時レビューを要求。 |
| Integration仕様欠落 | Task Issue・詳細設計あり | なし | 未実施 | `未通過`。実装を開始せず、Integration仕様作成・同時レビューを要求。 |
| 対が揃う | Feature仕様と受入仕様、同じRevision | TEST IDとREQ/ACの対応を確認 | Reviewer・判定・指摘状態を記録 | `通過`の場合のみ受け入れた入力、開始許可者・日時を記録して次工程へ進む。 |

各工程の具体的成果物、フォルダ、品質基準は対応する工程規約を参照する。開始条件が未達ならドラフト・調査のみを行い、終了ゲートを通過したと宣言しない。

### 工程状態と遷移

工程ごとの状態は成果物単位で管理し、状態名だけでなく入力・出力のRevisionと判定記録を必ず併記します。`Project Status`はIssue全体の作業進捗を示すAIDEの管理項目であり、個々の工程の開始可否・承認・検証結果を表しません。Issueが`In progress`でも未通過の工程は開始できず、Projectを`In review`にしても人間の承認やRelease Gate通過を意味しません。

| 工程状態 | 意味 | 遷移条件 |
|---|---|---|
| `未着手` | 工程の作業を開始していない。 | 入力正本・Revision、担当、開始条件を確定して`作成中`へ。 |
| `作成中` | 担当が成果物を作成・更新中。 | 出力正本を保存しRevisionを固定、検証計画を用意して`検証中`へ。 |
| `検証中` | 固定した入力・出力Revisionを対象に独立レビューまたはテストを実施中。 | 全必須確認が成功し未解決事項がなく、ゲート記録を完成して`通過`へ。失敗・必須指摘で`差し戻し`へ。人間判断が必要なら`承認待ち`へ。 |
| `差し戻し` | 検証失敗、必須指摘、または上流変更のため修正が必要。次工程は開始不可。 | 修正した成果物の新Revisionを記録し、旧判定を無効化して`作成中`へ。 |
| `承認待ち` | 権限を持つ人間の判断が未完了。 | 指定されたRevisionへの判断を記録。承認後、他のゲート条件も満たせば`通過`、却下・修正要求なら`差し戻し`。保留中は承認待ちを維持。 |
| `通過` | 記録したRevisionの検証・必要な承認が成立し、次工程へ渡せる。 | 入力または出力のいずれかが変わった時点で`変更により再確認待ち`へ。 |
| `変更により再確認待ち` | 通過時と異なるRevisionが関係する。旧検証・承認を新Revisionに適用してはならず、この状態では次工程を開始不可。 | 影響範囲・再確認対象を特定して記録する。成果物の修正が必要なら`作成中`、成果物は維持して検証・レビューのみをやり直すなら`検証中`、Human Gateの判断が未完了なら`承認待ち`へ移す。新Revisionに対する全必須確認後にのみ`通過`へ。 |

状態変更は履歴として追記し、過去の判定を上書きしません。成果物がGit管理下ならRevisionは完全なcommit SHAを使います。未コミット作業では`Draft`とし、共有可能な場合に限りbase SHA・対象パス・差分ハッシュ・取得元を記録します。参照できないRevision、曖昧な`latest`、日付だけの識別子は判定対象として認めません。複数入力がある場合は全て列挙し、各入力と出力の組み合わせを固定します。

### 工程記録テンプレート

工程ごとに以下を作業記録へ記入します。証跡は別の正本に保存してリンクし、記録には要約と取得可能な場所を残します。未実施は`未実施`と理由を記し、空欄を成功と解釈しません。

```markdown
## 工程記録: <工程名・実行ID>
- 状態: `未着手` | `作成中` | `検証中` | `差し戻し` | `承認待ち` | `通過` | `変更により再確認待ち`
- 入力正本・ID・Revision: <パス/URL、ID、完全なSHAまたはDraft識別情報。複数は列挙>
- 出力正本・ID・Revision: <パス/URL、ID、完全なSHAまたはDraft識別情報>
- 実行担当・実行ID・役割: <人/エージェント識別子、今回の呼び出しID、Generator/Reviewer/Test等>
- 実行日時・環境: <日時、環境・バージョン・構成>
- 検証: <観点/TEST ID、コマンド、結果 PASS/FAIL/BLOCKED/未実施>
- 証跡: <ログ・レポート等の正本リンクと取得方法>
- 独立確認: <確認者、対象入力/出力Revision、判定、指摘IDと状態。該当なしは理由>
- Human Gate: <対象仕様Revision、判断者、判断日時、承認/却下/保留、判断内容。不要なら理由>
- 未解決事項: <ID、内容、影響、担当、または「なし」>
- 次工程開始可否: `可` | `不可`。許可者・日時・受け渡す入力Revision: <値>
- 状態遷移・再確認理由: <日時、旧状態→新状態、変更されたRevision、無効化した判定>
- 再開位置・次の作業: <対象工程、未完了タスク/成果物、最初に行う確認、担当または依存先。中断なしなら「該当なし」>
```

次工程開始可否は機械的に「全入力Revisionが取得可能」「出力Revisionが特定済み」「必須検証・独立確認が対象Revisionに対して成功」「必須Human Gateがその仕様Revisionに対して承認済み」「未解決事項が開始を妨げない」「証跡を取得可能」の全てを満たす場合だけ`可`とします。一つでも未達・不明なら`不可`です。承認が不要な工程も不要と判断した根拠を記録します。

### Revision変更時の無効化とHuman Gate

検証結果・レビュー・承認は、記録に列挙された入力と出力Revisionの組にのみ有効です。いずれかが変われば当該判定を`変更により再確認待ち`として扱い、新Revisionへ自動継承しません。依存関係をたどって影響を受ける下流工程を特定し、再確認が必要な検証・レビュー・Human Gateを明記します。影響がないと判断した項目も、判断者・根拠・比較したRevisionを記録するまでは有効とみなしません。再確認完了後は新しい記録を作り、旧記録は監査可能な履歴として保持します。

Human Gateは承認時点の仕様正本の完全なRevision、承認者、日時、決定内容、対象範囲、条件・保留事項を一組で記録します。承認後に対象仕様のRevisionが変わった場合、旧承認は旧Revisionにだけ有効です。差分と依存先を確認して再承認要否を権限を持つ判断者が決定し、その判断（再承認要／不要、根拠、判断者、日時、新旧Revision）を記録します。影響有無が確定できない場合は再承認要として扱い、該当Gateを`承認待ち`に戻します。AIのレビューやQA判定から人間の承認を推定してはいけません。

**状態遷移の試行：** 入力仕様`S1`に対する検証`V1=PASS`とHuman Gate`H1=承認`を記録し、工程を`通過`・次工程開始可とします。仕様を`S2`へ更新した時点で旧記録を残したまま工程を`変更により再確認待ち`へ移し、`V1`と`H1`は`S2`の判定に利用できず次工程開始不可とします。`S2`を対象にした新しい検証`V2`と、必要な再承認`H2`を記録して条件が揃った場合にのみ、工程を再び`通過`・開始可とします。これにより古いRevisionの判定が変更後へ継承されないことを確認できます。

## サブエージェント呼び出し・引き継ぎ仕様

呼び出しは、役割・スキル・入力・範囲・出力・停止条件を明示した個別依頼とする。環境のサブエージェント機能が書き込み・実行・remote取得に対応するかを事前確認し、できない操作を完了したと報告させない。

```text
役割：<Generator / Reviewer / Test Designer / Test Executor>
スキル：<工程スキル名>
対象：<Feature/Task、Repository、branch、base/head SHA>
目的・完了条件：<Issue/仕様へのリンクと確認可能な条件>
入力正本：<必要最小限のパス、ID、参照URL。未確認は未確認と記載>
作業範囲・対象外：<明示>
出力先・形式：<正本パス、レビュー記録、テスト結果等>
制約：<既存変更保護、権限、機密、ツール制約>
停止条件：<仕様矛盾、OPEN判断、アクセス不能、必須ゲート未達等>

事実と推測を分け、対象Revision、変更ファイル、検証コマンドと実際の結果、
必須/提案指摘、未解決事項、次工程に渡すID・制約を報告してください。
未実行・失敗を成功と表現せず、対象成果物が共有先から取得可能か確認してください。
```

### GeneratorからReviewer/Testへの引き継ぎ

Generatorの成果物を書き出して対象Revisionを固定した後にのみ、独立Reviewer/Testを起動する。未コミット成果物を共有する場合、同一共有ワークスペース等から同一差分を取得できることを確認し、base SHA・対象ファイル・差分ハッシュ・取得方法を特定する。取得可能性がないレビューは完了扱いしない。

Reviewerには、Generatorの自己評価や結論を先に渡さず、対象仕様・対象差分・完了条件・レビュー観点を渡す。Test担当には期待結果の正本・テストID・実行対象Revision・コマンド・環境制約を渡す。独立実行とは別サブエージェント呼び出しであり、同じ実行会話で役割名だけを切り替えることではない。

結果受領後、Orchestratorは出力の存在・対象Revision・証跡・指摘の分類を読み戻す。結果が部分的、矛盾、欠落、取得不能の場合は当該ゲートを保留し、不足情報を明記して再依頼またはHuman Escalationする。

## 指摘修正回数とHuman Escalation

同一工程・同一対象成果物の指摘修正は、初回生成後の修正サイクルを最大3回とする。サイクルは「指摘を受領 → 対応または理由付き異議 → 更新差分を同じレビュアーまたは別の独立レビュアーへ再提示 → 結果記録」で1回と数える。修正内容が要件・設計・契約の変更を必要とする場合は、同工程内の修正で押し切らず、該当する上流工程へ戻す。

次の場合は3回を待たずに停止し、人間へエスカレーションする。

- 振る舞い・業務ルール・方式・リスク受容など権限者の決定が必要。
- 同一指摘の再発、レビュー担当間の相反、原因不明、要求と設計の矛盾。
- 秘密情報・セキュリティ事故、破壊的操作、許可範囲が不明。
- 対象Revisionや成果物の共有可能性を確認できず、独立検証が成立しない。
- 3回の修正サイクル後も必須指摘または必須テスト失敗が残る。

エスカレーションには、対象Revision、観測事実、関係ID、試行した修正回数と結果、選択肢・影響、必要な判断者、進行を止める範囲を含める。エスカレーション中は該当ゲートを未通過として保ち、承認を推測しない。

## サブエージェント失敗・中断・再開

サブエージェントが起動しない、タイムアウト、出力形式不正、成果物を共有できない、ツール権限不足などの場合、まず作業ツリーと出力先を読み戻して部分変更・副作用の有無を確認する。重複書き込みや外部操作の危険がない一時的な起動失敗に限り、同一入力で1回だけ再起動できる。実行中断後に処理状態や副作用が不明な場合は自動再起動せず停止し、状態確認または人間へエスカレーションする。

再起動しても失敗する、必須出力がない、役割分離を満たせない場合は、当該成果を不成立・未実行と記録する。Orchestratorが代筆してReviewer/Testの独立性を装ったり、失敗した結果を成功扱いしたりしない。

中断時は作業を安全な地点で止め、Issue等の作業記録に次を残す。再開時は現状を再読み込みし、記録のRevisionと一致しなければ引き継ぎ扱いにせず差異を調査する。

```markdown
## W-Model再開メモ
- 対象：Repository / Feature・Task / branch / base SHA / head SHA
- 完了工程・通過ゲート：<成果物パスとRevision>
- 作業中工程・サブエージェント役割：<状態、起動中か終了か>
- Generator/Reviewer/Testの出力：<取得可能な共有元と対象Revision>
- 検証済み：<コマンド、結果、証跡リンク>
- 修正サイクル：<工程ごとの回数／上限3>
- OPEN・未解決・失敗・未実行：<内容と影響>
- Human Gate/Escalation：<判断者、状態、停止範囲>
- 次の具体的作業：<担当役割と入力>
```

再開前に入力正本、branch/base/head、作業ツリー・未追跡ファイル、最新レビュー・テスト結果、Project/Issue状態を照合する。取得できない変更、所有者不明のファイル、実行中処理の可能性が残る場合は上書き・再実行せず、ブロッカーとして記録する。

## 完了判定

全工程で必須ゲートが通過し、トレーサビリティ・QAレポートが対象Revisionと一致し、Human Gate・PR・Release Gateに必要な人間判断が明示され、未解決事項が正直に開示されていることを確認する。本規約の最終成果はRelease Gateの判断記録であり、リリースの実施・稼働確認の完了を表さない。PR提出、マージ、Release承認、実リリースは別々の境界であり、一つの通過を次の承認とみなさない。AIDE採用RepositoryのIssue・PR・Project操作は [aide-workflow](../../skills/aide-workflow/SKILL.md) に従う。
