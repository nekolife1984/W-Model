# W-Model Traceability

対象Featureの成果物と対応関係を照合し、トレーサビリティ対応表と検出結果を更新します。規約は[トレーサビリティ検証](../../docs/w-model/06-traceability.md)、ID・正本・配置は[共通原則](../../docs/w-model/01-common-principles.md)に従います。

## 入力

- 対象Featureの識別子・範囲と、必要なら比較するbase/head Revision
- Feature仕様、Architecture、詳細設計、テスト設計、コード、実行結果の正本
- 既存の対応表、変更履歴、利用可能な検査スクリプト／CI

入力が見つからない場合は存在を仮定せず、未確認・不足として示します。既存の配置が確立している場合はそれを使います。

## 手順

1. 対象Repository・Revisionと成果物の正本・配置を確認し、Feature内のREQ・AC・DESIGN・TEST IDと廃止IDを抽出する。
2. 成果物からREQ→AC→設計→実装→テスト設計→実行証跡の対応をたどり、`docs/90-traceability/<feature>.md` または既存の対応表を生成・更新する。対応表の行はREQ単位とし、IDと相対リンクを使う。
3. base/headが与えられた場合は変更起点をREQ/AC、Architecture/ADR、DESIGN/IF/Task契約に分類して変更IDと旧/新Revisionを記録する。依存IDをたどり、下流の設計・実装・全テストレベル・Traceability・QAへの影響を直接/推移的に抽出する。影響ありは再確認対象、影響なしも新旧Revision・差分・依存IDを比較した根拠と確認者が必要。不明・比較不能を影響なしと推定しない。
4. REQの下流欠落、ACの受入検証漏れ、参照切れ、上流要件のない設計・コード・テストを双方向に検査する。共通基盤などの合理的な孤立理由が確認できたものは理由とリンクを記録し、問題として誤検出しない。
5. 適用性（適用/N/A）と実行状態（未設計/設計済み・未実施/成功/失敗）を区別する。N/Aは対象REQ・レベルごとに対象責務・リスク、根拠、残余リスク、代替検証ID・期待結果、再評価条件、独立確認者とRevisionを記録する。環境不足等で実行できない検証は未実施とし、必須テストの場合はQA BLOCKEDとして追跡する。全REQに全レベルのテストを一律要求しない。
6. 利用可能な自動検査を実行し、未導入ならその旨を明記してID・リンクと変更影響を手順に沿って照合する。検査方法、対象Revision、結果、検出事項、未解決事項を対応表と報告に残す。影響する検証結果・レビュー・承認は新Revisionで再確認するまでPASS/承認として扱わず、非影響判断も新しい影響評価記録として残す。成果物を修正した場合は検査を再実行する。

## 出力

- 更新した対応表と対象Revision
- 対応表の記録メタデータ: 比較対象Revision（変更影響分析時）、更新日、検査方法・コマンドと実際の結果（手動なら範囲・判断根拠）
- 検出事項一覧: 種別、対象ID／リンク、期待される対応、根拠、状態
- 未実装・未実行・適用外（理由付き）・失敗の明確な内訳
- 未解決事項と次に必要な作業

検出分類は少なくとも「未対応REQ」「参照切れ」「孤立成果物」「変更追随漏れ」「検証未設計」「未実行」「失敗」を扱います。状態や証拠が入力から確認できない場合、成功と推定せず未確認として報告します。対応表の生成・検査だけをもって品質承認やHuman Gate通過とはしません。

## 呼び出し例

```text
/w-model-traceability feature=customer-import base=main head=HEAD
```

```text
顧客取込Featureについて、正本と既存の対応表を確認し、REQから実行証跡までを更新してください。
base=main、head=HEADの変更影響も確認し、参照切れ・未対応REQ・孤立成果物・追随漏れを報告してください。
各テストレベルのN/AにはREQごとに対象範囲、根拠、代替検証、再評価条件と独立確認を記録し、環境不足等の未実施・BLOCKEDと区別してください。
```
